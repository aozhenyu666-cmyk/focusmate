## D-01 项目独立，旧项目只读

- 来源：执行指令 §0 第 1 条。
- 规则：新项目目录 `C:\focusmate`（工作区内通过 junction 可见为 `default-workspace\focusmate`），
  应用 ID `com.focusmate`，与旧「同桌」「莫宁」无共用代码、无共用签名。
- 现状：旧项目 C3 专注守护源码未落盘，只有文字记录 `_pet-reports/status-20261025/C3_FOCUS_GUARD_STATE.md`；
  其中记录的 F-01～F-08 八个已复现缺陷全部作为本次设计约束（见 D-09）。

## D-02 一期范围：只有"限制真实生效 + 到点真恢复"

- 来源：执行指令 §0 第 3、8 条。
- 规则：一期不含屏幕陪看、自动上网、B站/QQ、跨设备、多 Agent、向量库、复杂动画。
- 一期不含锁屏、挂起应用（SUSPEND）、停用应用（DEACTIVATE）、Force Stop、设备所有者。
  这些都要额外系统权限或重置设备，未取得授权前一律不做。

## D-03 「十分钟后再聊」只改对话跟进，不改锁定

- 来源：执行指令 §1.2 提供的默认规则。
- 规则：该句只修改跟进事项的下次时间，不改变专注会话的 `expiresAtMillis`。
  改变锁定时长必须走单独的确认流程（阶段 3 实现）。
- 实现：当前版本尚无对话与主动跟进（阶段 2），此规则先入档，阶段 2 必须遵守。

## D-04 提前结束：一期只提供"立即结束 + 留痕"

- 用户尚未在 A/B/C 三档中做出选择。
- 临时规则（覆盖层与通知栏两处出口都叫「紧急结束」）：
  立即解除，不等冷静期；但必须记入会话记录，且状态为 `USER_ENDED` 而不是 `COMPLETED`，
  以便复盘区分「到点结束」与「自己结束」。
- 待用户选择后按选择改写；若用户选「正常流程不能提前结束」，则移除 UI 出口，只保留故障恢复通道。

## D-05 主动交流：一期不实现

- 用户尚未确认主动交流的场景、频率、语音与否。
- 规则：本版本没有任何"角色主动开口"。UI 文案与通知也不暗示有人格存在。
- 依据：执行指令 §2 要求"不能只实现闹钟就宣称有活人感"，故宁可先不做。

## D-06 限制路径：无障碍前台识别 + 无障碍覆盖层（BLOCK 语义）

- 选择理由：不需要 root、不需要 Shizuku、不需要设备所有者、不清数据，是所有方案里唯一
  能在普通手机上立刻验证的强一档限制。
- 对照 DetoxDroid 三档：
  - BLOCK（覆盖层，要悬浮窗权限）→ 采用，但改用 `TYPE_ACCESSIBILITY_OVERLAY`，
    因为普通悬浮窗在部分厂商系统上会被"上层显示"策略削弱。
  - SUSPEND（要 Shizuku）→ 不采用，用户未授权装 Shizuku。
  - DEACTIVATE（要设备所有者）→ 不采用，需清设备数据。
- 真实强度声明（必须原样传达给用户）：
  - 能拦住：正常点图标、从最近任务切回、从通知打开。
  - 拦不住：用户去系统设置关掉无障碍或悬浮窗；用户在设置里强行停止本 APP；
    用户卸载本 APP。以上都属于"用户主动解除"，不做对抗。
  - 不承诺：锁屏状态下继续拦截（一期不做锁屏）。

## D-07 【用户新增】Gemini 沉浸舱：约十分钟内只允许 Gemini + 通话 + 微信

- 用户原话：「有一个功能…点开它之后，会弹出和 Gemini 对话的聊天，就是 APP，就切到 Gemini 的页面嘛。
  这个时候会维持大概 10 分钟左右，这个时候只能和 Gemini 对话。当然了，通话、微信这些还是能用的，
  但是别的 APP 都不行」。
- 落成规则：
  - 入口：首页按钮「进入沉浸舱 · 10 分钟」。
  - 动作：先落盘会话（`kind = GEMINI_DOCK`），再启动 Gemini，然后 1.2 秒后核验前台确实是 Gemini。
    核验不通过就是 `FAILED`（`TARGET_LAUNCH_FAILED` 或 `A11Y_UNAVAILABLE`），不显示为已开始。
  - 时长：默认 600000 ms（10 分钟），写在 `Presets.DOCK_DURATION_MILLIS`，UI 不硬编码。
  - 放行集合：Gemini 目标包 + 电话/Dialer/Telecom/InCallUI + `com.tencent.mm`（微信）
    + 系统界面/输入法/权限框/本 APP 自己（`AllowPolicy` 的 NEUTRAL）。
  - 其余应用：进入即显示全屏覆盖层，覆盖层吞掉返回键，提供「回到 Gemini」与「紧急结束」两个出口。
  - 到期：本地判定 `now >= expiresAtMillis`，直接解除，不等待模型或网络。
- 待确认的两个点（**必须由用户回答，不得自行假设**）：
  1. 「微信能用」是指微信整体可用（当前实现），还是只允许微信的音视频通话界面？
     若只要通话界面，就必须改成按 Activity/界面判定，强度与稳定性都会下降，且要重新验收。
  2. 10 分钟到期是直接放开全部（当前实现），还是先给一个确认步骤再放开？

## D-08 时间语义：墙钟存截止，单调钟只用同一次开机

- 规则：`expiresAtMillis` 是墙钟时刻，唯一持久化的时间；
  `SystemClock.elapsedRealtime()` 只在同一次开机内用于节流与 tick，**绝不存盘**。
- 用户改系统时间：`FakeClock.jumpWall()` 单测覆盖——改时间不会改写已存的截止时刻；
  但因为判定用墙钟，把系统时间往前调确实会让会话提前结束。这一点在验收里作为已知行为记录，
  不宣称"防改时间"。
- 重启：单调钟归零，会话按墙钟重新判定（`FakeClock.reboot()` 单测覆盖）。

# 阶段 2 决定

## D-11 一期采用「文字回复 + 系统 TTS」，语音输入不做

- 用户尚未明确答复（Q-08）。当前实现按执行指令 §1.2 的允许范围采用：
  - 文字**一定**展示（聊天界面 + 通知），不依赖 TTS；
  - TTS 是附加通道，失败只影响语音，不影响文字，也不改写"已经说过"的事实；
  - **不做**语音输入：没有麦克风权限申请，没有 ASR。
- 记录粒度（对应执行指令任务 2.3）：生成完成 / 文字展示 / TTS 开始 / TTS 完成 / TTS 失败
  分别留痕，见 `DeliveryTrace`。**不记录"已读"**，因为通知发布不等于用户看到。

## D-12 Android 后台调度：前台服务 60 秒 tick + AlarmManager 兜底，不承诺准点

- 不用 WorkManager：最小周期 15 分钟，对"到点主动说话"太粗，且同样不保证准时。
- 用 `CompanionService`（前台服务）每 60 秒判定一次；真正的到期时刻由
  `ExpiryScheduler` 的闹钟在上层纠正（迟到的结果会被 `DeliveryGate` 判为"迟到"或直接发送）。
- **明确不承诺**：
  - Doze / 厂商省电会推迟；
  - 息屏后 tick 可能被系统降频；
  - 「强行停止」后不会恢复（Android 不给任何广播），要靠用户重新打开。
- 迟到处理：超过 `DeliveryGate.MAX_LATE_MILLIS`（6 小时）不再补发；
  6 小时内允许发，但 UI 上不声称"准时"。

## D-13 主动程度：默认只在「有依据」时开口，主动闲聊默认关闭

- 用户尚未确认（Q-05、Q-09）。当前实现把最保守的一档设为默认：
  - 只对**用户约定**与**对话里没说完的事**开口；
  - `allowSmallTalk = false`：不会凭空找话说；
  - 频率：两次之间 90~240 分钟、每天最多 3 次、23:00-08:00 免打扰
    （上游 SurfCore 默认是 2.5~5 小时 / 每日 4 次 / 23:30-08:30，本项目刻意更少）。
- 允许开启主动闲聊时（`allowSmallTalk = true`）也必须满足：
  依据来自真实旧事实（`FactEngine.recall`）或人格兴趣，**禁止固定台词轮播**；
  没有依据就 `SchedulePolicy` 返回 `no-topic`，不说话。

## D-14 「十分钟后再聊」只改跟进事项，不改锁定（落地 D-03）

- 实现位置：`IntentParser` 把这类句子解析为 `POSTPONE`，
  `CompanionRuntime.userSays` 只调用 `FollowUpEngine.userAgreement`，
  完全不触碰 `FocusSession.expiresAtMillis`。
- 反例也处理了：句子里出现「缩短专注/延长专注/提前结束专注」等，解析为
  `LOCK_CHANGE_REQUEST`，回复明确拒绝并指向首页入口，**不执行**。
- 单测：`IntentParserTest.要求缩短专注 …`、`FlowTest.B 改期后旧事项失效`。

## D-15 记忆更正与遗忘：墓碑而非删除

- 事实有三种来源：`USER_STATED` / `SYSTEM_OBSERVED` / `MODEL_INFERRED`，界面显示为
  「你说的 / 我看到的 / 我猜的」，模型推测的重要度被压到 0.6 倍，防止猜测变成"用户说过"。
- 更正 -> 旧条目 `SUPERSEDED` 并指向新条目；遗忘 -> `RETRACTED`。
- 上下文只从 `ACTIVE` 拼，所以旧内容不会通过任何摘要复活。
- **注意（不许美化）**：墓碑仍在磁盘上，这不是"彻底删除"。用户若要物理删除，
  需要另做导出/清理功能，一期没有。


## D-16 「已经说过」与「这件事了结」分开（云端复测 F-03）

- 引入 `AWAITING_REPLY`：主动发出去之后进这个状态，只有**用户回应**才转 `DONE`。
- 之前把发出去的立刻当 `DONE`，又让「用户任何一句话」把全部 open 事项结算成 `DONE`，
  结果是一句无关闲聊就把明天的约定抹掉。这是产品语义错误，不是代码小 bug。
- 现在的规则：`closeOnUserReply` 只处理 `AWAITING_REPLY`；`PENDING`（还没到期）一律不动。

## D-17 遗忘与更正作用于「所有模型输入」，但不必抹掉界面历史（云端复测 F-02）

- 用户说忘掉一件事，要同时处理三处，缺一处就会漏：
  1. 事实 -> `RETRACTED`；
  2. 产生它的那句话 -> `Utterance.hidden = true`（界面仍显示，不再进模型输入）；
  3. 以那句话为**唯一依据**的待跟进事项 -> `CANCELLED`。
- 为什么不是全局删词：用户之后自己再提一次是"重新提供"，不是"系统复活"，两者必须区分。
- 界面保留可见是有意的：用户需要能看到"我让你忘掉的东西确实还在本地，只是不再说给模型听"。
  这也不是物理删除（D-15 的说明仍然有效）。
- **诚实标注**：墓碑式处理意味着磁盘上仍有原文。若要做到物理清除，需另做导出清理功能，一期没有。

## D-18 记忆版本与专注状态都要参与输出校验（云端复测 F-05）

- 新增 `CompanionState.memoryVersion`：**只**在事实增删改、对话追加、配置变更时 +1。
  不复用 `epoch`，因为 `epoch` 连"标记投递中"这种记账也会变，拿它校验会把正常投递判成过期。
- 输出前除事项版本外，还检查：
  - 记忆版本是否仍等于发起时的值；
  - 此刻是否仍允许开口（免打扰 / 专注中 / 开关），由 `SchedulePolicy.evaluate` 复算一次。
- 理由："生成开始时允许、生成结束时已经禁止"是真实场景（用户正好进入专注）。
